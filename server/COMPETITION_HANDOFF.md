# Sahne Plus — competition deployment gate
## Implemented
- /basvuru: full name, phone, private video, pilot adult eligibility, versioned participation agreement, Turnstile and private status code.
- /yarismalar and /siralamalar: approved and separately published videos only; server-side ranking and verified account votes.
- /basvuru-inceleme: token-authenticated review, accept/reject, separate publication permission and moderation confirmation, private video access, email retry and manual phone contact record. No public personal phone or applicant full name.
- Worker and D1 schema are staged, NOT wired into production wrangler.toml.
## Before real data collection
1. Review/approve participation terms and privacy notice including phone processing, controller identity, retention period, applicable lawful bases, minors and cross-border transfers. 18+ and 25 MiB are interim pilot choices, not owner-approved rules. Define retention and deletion/withdrawal operational process, malware/media review or transcoding pipeline, anti-abuse limits and staff access logging. Do not open form before these controls are verified.
2. Use isolated staging resources. Create or identify D1 DB (binding DB) and private R2 bucket (VIDEOS); do not enable public bucket URL. Apply server/competition-schema.sql. Configure static assets binding ASSETS and API-only run_worker_first ["/api/competition/*"], and main="server/competition-worker.mjs" in a staging Wrangler config. Existing production config is unchanged.
3. Configure Turnstile site and secret for staging origin; set ALLOWED_ORIGIN to exact https origin. Use a verified transactional mail sender and the actual authorized review mailbox via REVIEW_FROM and REVIEW_TO; no real mail recipient is assumed. RESEND_API_KEY secret. Review e-mail contains application ID only, not the video or phone. "sent" means provider accepted request, not inbox delivery. Retry with admin console; validate inbox delivery.
4. Configure REVIEW_TOKEN as >=32 random characters via secret and restrict /basvuru-inceleme and /api/competition/admin/* using staff access controls; never expose token in source or URL. Prefer individual staff identities and audit before launch. Use AUTH service binding to trusted existing identity provider returning verified=true and stable sub for authenticated session. VOTER_HASH_SALT secret. No anonymous vote.
5. Test disabled states, valid and malformed uploads, duplicate retries, private video access, e-mail failure and retry, status code isolation, approval/rejection, explicit publish/unpublish, same-account duplicate votes and ties, cross-origin rejection and mobile layout. Test deletion and data retention procedures separately. Run actual build and integration tests in staging.
6. Only after all gates and owner approval, set APPROVED_TERMS_VERSION=SP-2026-11-26-v1 (or revised version matched in code) and APPLICATIONS_OPEN=true. VOTING_OPEN=true only after verified account and contest rules approved. Manual phone communication is currently recorded by staff; no automated SMS or WhatsApp integration. MOV may be privately reviewed but cannot publish until safely converted to supported format; no fake success.
